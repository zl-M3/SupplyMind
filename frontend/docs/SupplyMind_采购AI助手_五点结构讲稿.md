### 一句话定位

> 这不是"给采购系统加个聊天框"，而是**把采购员每天在做的四件事——找供应商、算买多少、盯到货、对异常——做成了可测试、可审计、可撤销的七条编排流程**，模型只负责理解与表达，数字和动作全部走确定性代码。

## 一、第一点：项目起因、痛点

### 1.1 业务场景

中型制造与零售企业的采购域，日常跑的是这样一条链：**需求 → 选供应商 → 下采购单 → 审批 → 发货 → 到货 → 收货入库 → 对账**。

系统已经有了（采购单、供应商、物流、库存都在库里），但**系统只记录，不协助**：它告诉你"这单还没到"，不告诉你"该不该催、催谁、催了会不会白催"。

### 1.2 目标用户与原有方式

| 角色 | 每天在做什么 | 原有方式的痛点 |
|---|---|---|
| **采购员**（主用户） | 建单、比价、催货、处理延迟 | 在 4 个页面之间来回切，靠 Excel 辅助，信息靠人拼 |
| **采购主管** | 审批 5～20 张待审批单 | 只看得到金额和商品，看不到"这单贵不贵、急不急、有没有重复" |
| **采购负责人** | 看供应商表现、控风险 | 每月手工拉数，口径各算各的 |

### 1.3 四个具体痛点（每条都能在架构里找到对应解法）

**痛点一：算"买多少"靠拍脑袋。**
补货量的正确算法是 `max(0, 安全库存 − 当前可用 − 已审批未收货)`，但"已审批未收货"散在采购单明细里、"当前可用"散在三个仓库里。采购员懒得逐个加，通常按经验报个整数量。**结果是一边压库存、一边断货。** → 对应：`calc_replenishment_need` 计算工具 + 库存只读跨域视图。

**痛点二：选供应商靠记忆和微信。**
同一品类有三五家供应商，各自的价格、账期、起订量、准时率都在不同地方。比价基本是"上次找的是老张，还找老张"。**没有报价历史表，所谓比价就是凭印象。** → 对应：`supplier_quotes` 表 + `calc_supplier_score` 多维打分（硬约束过滤后加权）。

**痛点三：异常只有"报警"，没有"判断"。**
物流超期 3 天，系统弹个红点就完了。采购员要自己去查：这单关联哪些客户订单？库存还撑几天？换供应商来得及吗？合同能不能索赔？**这一步平均要翻 4～5 个页面、花 20 分钟以上。** → 对应：B2 到货异常处置工作流（影响面计算 + 方案候选 + 合同条款引用）。

**痛点四：审批是"闭眼签字"。**
主管打开一张单，只看到金额和商品。他不知道这张单的单价是否偏离历史 15%、不知道同一商品上周刚买过、不知道供应商资质快过期。**审批本该是风险闸门，实际成了流程盖章。** → 对应：A3 待审批单审阅工作流（规则化体检 + 制度引用，只出意见不改状态）。

### 1.4 项目目标与边界

**目标**：把采购员单次任务的跨页面操作，压缩成"说一句话 → 看一张卡 → 点一次确认"。

**明确不做**（写进稿里能挡掉一半追问）：

- 不做无人审批的自动采购——审批是制度上的人的决定权；
- 不做对外沟通（不直接发消息给供应商），只起草话术；
- 不做供应商评分卡模型训练，首期用规则加权；
- 不做跨企业比价（只在本企业历史成交价与在册供应商报价内求解）。

### 1.5 业务价值（换算成老板听得懂的语言）

| 价值 | 机制 | 指标 |
|---|---|---|
| 人效 | 建单、催货、异常分析从"翻页面"变成"问一句" | 单次任务耗时、页面跳转次数 |
| 准确 | 补货量、比价、影响面全部由代码算 | 草稿字段正确率、比价采纳率 |
| 风控 | 审批前自动体检，AI 无审批权限 | 审批驳回率、异常单拦截数 |
| 成本 | 减少压库存与紧急采购 | 库存周转、紧急采购占比 |

## 二、第二点：项目架构

### 2.1 分层（讲法 A：按系统分层）

| 层 | 名称 | 负责内容 |
|---|---|---|
| **L1** | 接入层 | 采购订单页、供应商页、物流详情页的"问 AI"入口；全局抽屉；页面上下文注入 |
| **L2** | 意图与路由层 | 判定 7 条工作流中的哪一条 + 抽取槽位；**路由错了后面全错**，所以这一层有置信度阈值与兜底 |
| **L3** | 编排层（LangGraph 子图） | 每条工作流一个子图：节点、条件路由、人工打断点、checkpoint |
| **L4** | 工具层（19 个受控接口） | 查询 7 / 计算 5 / 写 4 / 知识 3；**按工作流动态裁剪，每轮暴露 ≤7 个** |
| **L5** | 确定性计算层 | 补货量、价格基准、供应商评分、影响面、异常检测——**有唯一正确答案的，一律不交给模型** |
| **L6** | 知识层（五层 RAG） | 制度 / 合同 / **口径** / 案例 / 品类；带元数据与有效期过滤；引用到条款级 |
| **L7** | 治理层 | 审批入口**不存在**、写操作前置拦截、幂等键、二次确认、agent_audit_log |
| **L8** | 数据层 | 20 张表、31 条关系；业务规则用 CHECK / UNIQUE / 事务下沉到库里 |

**一句话记法**：L2/L3 解决"走哪条路"，L4/L5 解决"算得准"，L6 解决"依据在哪"，L7 解决"敢不敢动手"。

### 2.2 主链路（以 A1 建单为例，完整走一遍）

> 用户："帮我给华东仓补一下五层瓦楞纸箱，下周一到货"

| 步 | 节点 | 动作 | 产出 |
|---|---|---|---|
| 1 | 意图路由 | 命中 `A1_create_order`，置信度 0.9+ | `workflow=A1` |
| 2 | 槽位抽取 | 商品=PRD-001、仓库=WH-01、到货=下周一 | `slots`，`missing=["qty","supplierId"]` |
| 3 | 澄清 | **一次只问一个**：先问数量还是先问供应商？按业务优先级只问供应商 | 用户回答 |
| 4 | 数量计算 | `calc_replenishment_need`：800 − 120 − 200 = **480** | 数量 + 计算依据 |
| 5 | 供应商候选 | 按商品品类 → `supplier_categories` 桥表 → 2 家合规供应商 | 候选池 |
| 6 | 定价 | 取最近成交价 / 在册报价；`calc_price_benchmark` 判偏离 | 单价 + 偏离度 |
| 7 | 前置校验 | 起订量、供应商状态、`check_order_anomaly` 查重复单、金额阈值 | 通过 / 拦下 |
| 8 | 草稿卡片 | 商品 / 数量 / 单价 / 金额 / **计算口径** | 人工确认 ✅ |
| 9 | 写入 | `create_purchase_draft`（幂等键） | 采购单号 |
| 10 | 收尾 | 问"是否立即提交审批"（二次确认） | 结束或进入审批流 |

### 2.3 简单任务为什么不走全流程

用户只说"华东仓纸箱还有多少" → 走**短路**：意图路由 → `query_inventory_snapshot` → 直接答。跳过澄清、计算、校验、确认，节点数从 10 降到 2。

**这是必答题**："为什么不是所有请求都过一遍全部节点？"——采购域里查询类请求占【X%】，全走全量流程会让 P95 从【Y】秒涨到【Z】秒，而且多节点多一次幻觉面。**路由的价值就是让简单的事便宜地做。**

### 2.4 异常链路（第三类流程，面试必问）

| 异常 | 触发点 | 处理 | 兜底 |
|---|---|---|---|
| 供应商已停用 | 候选池构建 | 剔除并给出 2 个备选 | 不生成草稿 |
| 数量低于起订量 | 前置校验 | 提示 MOQ，建议取整到倍数 | 允许用户坚持 |
| 检出重复单（7 天内同商品同供应商未完成） | `check_order_anomaly` | **拦下**，展示已有单号，让用户选"合并 / 仍新建" | 默认不建 |
| 工具接口超时 | 任一工具 | 重试 ≤2 次，**写请求只查单不重发** | 降级为"手动建单" |
| 模型输出不合 schema | 校验节点 | 带错误回喂重试 ≤2 次 | 降级到模板草稿 |
| 工具调用超预算 | 编排层 | 强制收口，输出部分结果 + 失败原因 | 不静默失败 |
| 用户中途改数量 | 任意节点 | 只重算受影响字段，不重跑全流程 | — |

**三个字段要能讲透**：

- `slots.missing` → 决定澄清策略，**一次只问一个**，避免变成问卷；

## 三、第三点：项目难点与解决办法

> 三个难点分别来自：业务语义 / 技术效果 / 工程治理。第四个是备用。

### 难点一（业务语义）：同一个"准时交付率"，列表页、报告、AI 回答给出三个不同的数

**问题场景**：主管在供应商列表看到某家准时率 50%，点进 AI 报告却写 67%，问一句 AI 又说"约 60%"。

**具体表现**：三个入口三个数。更糟的是**每个数单独看都"有道理"**，用户不会立刻发现错，但一旦发现就完全不信系统了。

**业务影响**：这是**信任级故障**。采购域的指标直接决定"这家供应商该不该降级"，口径不一致等于把决策建在沙子上。

**排查过程**：

1. 一开始以为是数据不同步，加了对账，发现数据一致；
2. 逐个入口对代码，发现三处各算一遍：
   - 后端视图（拟）按"已完成订单"算；
   - 前端 `rules.ts` 按"已完成且存在预计到货时间"算；
   - AI 的提示词里让模型"根据订单列表估算"——**模型自己数点数，四舍五入还出错**；
3. 再往下查，还有更隐蔽的：**样本量的判定也不一致**——一个入口把 1 单的样本当有效（100% 准时率），另一个入口显示"数据不足"。

**根本原因**：**指标定义不是代码，是散落在各处的口头约定。** 没有单一数据源，也没有地方声明"这个词到底什么意思"。而模型一旦参与计算，它连"分母是什么"都不知道。

**解决方案（四层）**：

1. **口径层进知识库**：把"准时交付率 = 分子/分母/样本不足阈值/起算日"写成结构化文档放进 L3 口径层，**有版本号**；
2. **计算下沉到视图**：`v_supplier_ontime(supplier_id, completed_cnt, ontime_cnt, ontime_rate, sample_enough)`，三个入口全部读同一个视图；
3. **AI 不给算的机会**：模型只调 `get_supplier_profile` 拿现成数字，**提示词里明确禁止自行计算或估算**；
4. **样本不足显式化**：`sample_enough` 是个字段，不是判断逻辑，前端统一显示"数据不足"。

**验证**：构造 30 家供应商的测试数据（含 0 单、1 单、2 单、10 单四档样本），三个入口各取一次，**数值必须完全一致**；再断言 1 单样本必须显示"数据不足"。

**结果与剩余边界**：口径一致性 100%。剩余问题是**新指标加入时仍会漏**——所以把"新增指标必须先进口径层"写进了评审清单，这是流程问题不是技术问题。

---

### 难点二（技术效果）：19 个工具全交给模型，它会选错，而且错得很像对的

**问题场景**：用户说"纸箱快没了，帮我补一下"。模型调了 `query_purchase_orders` 而不是 `calc_replenishment_need`，给出的答案是"你还有 3 张在途采购单"——**听起来完全合理，但答非所问**。

**具体表现**：工具选择准确率只有【X%】。错误集中在三组易混工具：补货计算 vs 查采购单、查供应商 vs 查报价、查物流 vs 查采购单。

**业务影响**：这类错误**不会报错、不会崩溃**，只会给出一个"看起来对"的答案。用户按它建单，数量和现实脱节——比直接失败更危险。

**排查过程**：

1. 先怀疑模型能力，换成更强的模型，只从【X%】提到【Y%】，**说明上限不在模型**；
2. 拉 `ai_tool_calls` 的调用明细看参数，发现**很多次调用本身是合理的**（参数对、格式对），只是"不该在这个时刻调"；
3. 进一步做归因：把错误样本按"当时上下文里挂了几个工具"分组，**挂 16～19 个工具时错误率是挂 4～6 个时的【Z】倍**；
4. 结论：**问题不在选哪个工具，而在于一次给它的选项太多。** 工具描述之间有语义重叠（"查询采购单"和"计算补货量"都涉及采购单），模型被相似描述干扰。

**根本原因**：**把工具当成能力清单暴露给模型，而不是当成"当前这一步能用的手段"。** 一个人做"补货"这件事时，脑子里不会同时想着"查物流"，模型也不该。

**解决方案**：

1. **工作流先行**：先把请求路由到 7 条工作流之一，**每条工作流只挂自己的工具子集**（4～6 个）；
2. **工具描述去重**：每个工具的描述里写清"**什么时候不该用我**"，例如 `query_purchase_orders` 的描述末尾写"如果你要算数量，不要用我，用 calc_replenishment_need"；
3. **参数 schema 强校验**：入参走 JSON Schema，不合格不执行直接回喂错误；
4. **前置槽位检查**：缺关键槽位（如 productId）时**先澄清，不调工具**——相当一部分错误调用其实是"信息不够硬猜"。

**验证**：按工作流分组构建 200 条工具选择评测集（每条标注"应调哪些工具、不应调哪些"），比较"全量 19 工具" vs "裁剪后"选择准确率：【A%】→【B%】，平均工具调用次数从【m】降到【n】。

**结果与剩余边界**：准确率【B%】，成本同时下降。剩余问题是**跨工作流的复合请求**（"帮我把延迟那单补一下"同时涉及 B2 和 A1），现在会拆成两轮对话，体验上多一次确认——这是下一阶段要做的子图嵌套。

### 难点三（工程治理）：AI 建草稿，一次点击产生了两张采购单

**问题场景**：用户在确认卡片上双击"确认创建"，或网络重试，产生了**两张一模一样的采购草稿**。

**具体表现**：并发压测中，同一 payload 提交 100 次产生【3】张单；越权用例（停用供应商、超金额阈值、无授权提交审批）拦截率只有【X%】。

**业务影响**：重复采购单会走两遍审批、可能真的下两次单、到货后收货数量翻倍。**这是资金与账实问题，一次就够毁掉信任。**

**排查过程**：

1. 起初靠前端按钮 loading 防重，压测一上并发就击穿；
2. 看 `agent_audit_log` 和接口日志，发现 `create_purchase_draft` 被调了 3 次——**模型调用本身不确定 + 工具层超时重试**，同一次意图被放大；
3. 越权漏检的根因更直接：额度校验写在**提示词**里，模型"理解了"但没执行，而且校验点在模型之后，**模型可以绕过**；
4. 结论：**凡是涉及资金和不可逆动作的约束，放在模型这一侧就等于没有。**

**根本原因**：**提示词是"建议"，不是"约束"。** 概率模型无法提供"只执行一次"这种确定性保证；而这本质是分布式系统的幂等性和访问控制问题，必须在模型之外解决。

**解决方案（把约束下沉）**：

1. **审批入口根本不存在**：四个危险动作（审批、收货、停用供应商、改价）**不注册成工具**，模型没有这个能力，不是"被拦住"而是"够不着"；
2. **幂等键**：`user_id : workflow : draft_version : hash(payload)`，服务端唯一索引；重复键**幂等返回首次结果**而不是拒绝；
3. **重试纪律**：写请求超时只做"按幂等键查单确认"，**绝不盲目重发**；
4. **前置拦截器**：额度、供应商状态、金额阈值、白名单，全部在 `create_purchase_draft` 的服务端入口校验，模型绕不过；
5. **二次确认点**：金额超阈值、命中替代供应商 → `interrupt()` 挂起，人确认后从 checkpoint 恢复；
6. **全链路审计**：`agent_audit_log` 记 `actor_type(agent/human) / action / target / before / after / idempotency_key / model_version`。

**验证**：幂等压测（同 payload 并发 100 次 → 恰好 1 张单）；越权用例集【N】条 → 拦截率必须 100%；审计还原（随机抽 10 张单，能否还原"为什么是这一版草稿"）。

**结果与剩余边界**：越权 100%、零重复单。剩余问题是**用户授权意图的表达精度**——"随便买，别超 5000"里的 5000 是单笔还是累计、含不含税，仍有歧义，需要产品层设计更明确的授权 UI。

### 难点四（备用）：RAG 引用了一份已经失效的合同

**场景**：AI 回答"该供应商延期可主张 5% 违约金"，引用的条款来自一份**去年到期**的框架协议。

**根因**：语料只按语义相关性检索，**没有版本与有效期过滤**。合同一年一签，旧版本还留在库里。

**方案**：切分时把 `version / effective_from / effective_to / supplier_id` 写成 chunk 元数据；检索**强制**加时间窗口过滤；出答案前校验引用的 `doc_id + clause_no` 必须真实存在且当前有效。

**验证**：故意放入一份已过期合同，检索必须命中不到；引用校验脚本对全部报告跑一遍，命中率必须 100%。

> 这个点很值钱，因为它证明你想到的是"**RAG 什么时候会害死人**"，不是"我搭了个 RAG"。

## 四、第四点：技术讲解

> 每项按五问法：用在哪 / 解决什么 / 原理 / 为什么选 / 限制与替代。

### 4.1 LangGraph 子图编排

- **用在哪**：7 条工作流各一个子图，共享一个 State。
- **解决什么**：多步依赖、条件路由、人工打断、失败可恢复。
- **原理**：把流程建模成有向图，节点读写共享 State，边可以是条件边；每次状态变更落 checkpoint；`interrupt()` 让图在指定节点暂停并持久化，外部恢复时从断点继续。
- **为什么选**：这流程天然是图——有回边（校验不过重来）、有分支（简单/复杂）、有中断（确认点）。用 while 循环也能写，但要自己做检查点、恢复、可视化；**它的真实价值是"可观测 + 可恢复"**。
- **限制**：图一复杂调试成本高；State 设计不好会变成全局大对象。**它管"怎么走"，不管"能不能做"**——权限、预算、幂等得自己写。替代：自研状态机（可控但工作量大）。

### 4.2 工具集裁剪与窄接口

- **用在哪**：19 个工具，每轮只暴露 4～7 个。
- **解决什么**：工具语义重叠导致选错（难点二的直接解法）。
- **原理**：意图路由先定工作流，工作流声明自己需要哪些工具，编排层按声明注册工具集。
- **为什么选**：模型选工具本质是"分类"，**类别数越多越容易错**。裁剪不是省 token，是把分类问题的候选集从 19 降到 5。
- **限制**：跨工作流请求需要多轮；工具子集与工作流耦合，新增工作流要同步维护映射表。替代：工具分两层（领域工具 + 复合工具），但对模型透明，难调试。

### 4.3 确定性计算层（补货 / 评分 / 影响面 / 异常检测）

- **用在哪**：L5，是"这个数对不对"的裁判。
- **解决什么**：模型算不对、算慢了、算错了还没法审计。
- **原理**：
  - 补货：`max(0, 安全库存 − 可用 − 已审批未收货)`；
  - 评分：**硬约束先过滤**（资质有效期、品类授权、MOQ），余下四维加权（准时率 0.35 / 报价偏差 0.25 / 提前期满足 0.25 / 账期距离 0.15）；
  - 影响面：缺口 = 需求 − 可用 − 可及时到的在途；在险金额 = 缺口 × 单价；
  - 异常：重复单（7 天同商品同供应商未完成）、单价偏离（vs 中位数 > 15%）、数量异常放大、创建人 = 审批人。
- **为什么选**：这些是**有唯一正确答案**的问题，用概率模型去解是原则性错误。而且确定性代码**可测试、可解释、可审计**——面试官问"怎么保证算对了"，答案是"这一步不是模型做的"。
- **限制**：规则要业务方持续维护；加权系数是拍的，没有数据支撑。替代：整数规划（更通用但更重）、小模型学排序（更好但不可解释）。

### 4.4 五层 RAG 与引用校验

- **用在哪**：D1 问答、B2 的合同条款、C1 的案例参考。
- **解决什么**：制度与合同知识不在模型里，且**会过期**。
- **原理**：制度 / 合同 / **口径** / 案例 / 品类五层；**按条款切分**（不是按字数），chunk 带 `doc_type / supplier_id / clause_no / version / effective_from / effective_to`；检索走混合检索 + metadata 过滤 + **有效期强制过滤**；输出必须引用到条款级。
- **为什么选**：合同"一年一签"这个业务事实，决定了**没有版本过滤的 RAG 一定会答错**，而且是危险的错（告诉你能索赔，实际不能）。
- **限制**：元数据要人维护，漏标就是坑；条款切分粒度不好会让引用变成断章取义。替代：结构化抽取成表格（更准但不通用）。

### 4.5 幂等与审计

- **用在哪**：所有写工具。
- **解决什么**：重复下单、越权、事后说不清。
- **原理**：幂等键 = `user : workflow : version : hash(payload)`，服务端唯一索引；审计表记 before/after。
- **为什么选**：这是"敢让 AI 动手"的前提。**能聊天不算能力，能安全地花钱才算。**
- **限制**：多一层延迟；审计表增长快，要归档。替代：无（这个不能省）。

### 4.6 数据库约束下沉

- **用在哪**：`purchase_orders` 的 `CHECK (approver_id IS NULL OR approver_id <> created_by)`、`warehouse_stock` 的 `UNIQUE(product_id, warehouse_id)`、收货的"先整体校验再统一写"。
- **解决什么**：业务规则只存在于应用层，换个入口就能绕过（AI 就是那个新入口）。
- **原理**：把"不会变的规则"写成库约束，应用层和 AI 层都绕不过。
- **为什么选**：**加了一个新入口（AI）之后，最省事的做法不是给新入口补校验，而是把校验挪到绕不过去的地方。** 这个视角在面试里很加分。
- **限制**：约束改起来要迁移；复杂的跨表规则（如调拨校验）还是得在事务里写。替代：触发器（不推荐，难维护）。

### 4.7 可观测（ai_tool_calls 聚合）

- **用在哪**：`ai_tool_calls` 独立成表。
- **解决什么**：出问题不知道是哪个工作流、哪次调用、哪条规则。
- **原理**：每次调用记 `name / params / status / duration_ms / task_id`，可按工作流聚合出**工具失败率、P95 耗时、平均调用次数**。
- **为什么选**：难点二和难点三的排查**完全依赖这张表**。没有它，"工具选错"只能靠猜——而"靠猜"是面试里最容易被识破的描述。
- **限制**：params 可能有敏感信息，要脱敏。

### 4.8 相近概念必须能区分（加分项）

| 概念 | 回答什么 | 本项目对应 |
|---|---|---|
| LangGraph | 流程怎么执行 | 7 条工作流子图 |
| 治理层 | 允许做什么、最多几次 | 审批入口不存在、幂等、预算、审计 |
| 工作流 | 这类任务按什么顺序做 | A1/A2/A3/B1/B2/C1/D1 |
| 工具 | 拿确定性数据 / 执行受控动作 | 19 个窄接口，按工作流裁剪 |
| 计算层 | 数字谁算 | 补货、评分、影响面、异常检测 |
| 知识库 | 规定是什么 | 五层语料，带版本与有效期 |

## 五、第五点：项目优化（版本演进）

### V1（跑通）：一个 Prompt + 一把梭工具

做法：把 19 个工具全注册给模型，让它自己判断调什么；补货量让它"根据库存估一个"；草稿生成后直接写库。

暴露的问题：

- 工具选错率高，答案"合理地错"；
- 补货量估算不准，草稿一改再改；
- 准时率三个入口三个数；
- 重复建单；
- 出错无法定位。

### V2（效果与正确性）：拆工作流、计算下沉、工具裁剪

改动：

1. 引入 7 条工作流子图，每条只挂自己的工具；
2. 补货量、评分、影响面全部改由代码算，模型只解释；
3. 工具描述加"什么时候不该用我"；
4. State + checkpoint，校验不过只回退到受影响节点，不重跑全链；
5. 结构化输出 + schema 校验节点。

收益：工具选择准确率【A%】→【B%】，草稿字段正确率【X%】→【Y%】，平均工具调用次数【m】→【n】。

代价：从"一个文件"变成"分层架构"，调试面变大；每个工作流要做自己的评测集。

### V3（当前，可信与可运营）：治理与口径

改动：

1. **审批入口根本不存在**——危险动作不注册成工具；
2. 幂等键 + 重试纪律；
3. 二次确认点 + `interrupt()` 恢复；
4. `agent_audit_log` + `ai_tool_calls` 全链路可回放；
5. **口径层进知识库 + 视图固化**，三个入口读同一个数；
6. 合同语料加版本与有效期过滤，引用必须校验存在；
7. 200 条工具选择评测集 + 30 条口径一致性用例 + 故障注入。

收益：越权拦截 100%、零重复单、口径一致性 100%、可 5 分钟定位到节点与规则。

代价：每次写操作多一层校验；审计表增长快；工作流与工具映射要维护。

### 下一阶段

1. **补 `supplier_quotes` 表**，把 A2 比价从"比历史成交价"升级到"多供应商在册报价 + 提前期"的完整比价；
2. **工作流嵌套**：处理"帮我把延迟那单补一下"这类跨工作流复合请求；
3. **主动巡检**：B1 从"人问"变成"每天 9 点推"，并接入拣货产能约束；
4. **小模型固化**：用真实（脱敏）数据做小规模 SFT，固化"意图 → 工作流"的路由，降本提速——前提是**事实来源不变，只学路由与格式**；
5. **评测集扩容**：200 → 1000 条，接入线上 A/B。

## 七、追问清单（20 题 + 答法要点）

| # | 追问 | 答法要点（三句内） |
|---|---|---|
| 1 | 为什么一定要 Agent，加个搜索框不行？ | 多步依赖 + 带副作用写库。搜索框只能查，不能"算完再建单"。 |
| 2 | 为什么是 7 条工作流而不是 7 个 Agent？ | 共享一套工具和 State；拆成 7 个 Agent 就是重复实现查询逻辑。工作流是编排模板不是角色。 |
| 3 | 为什么不让模型自己算补货量？ | 有唯一正确答案；代码可测试可审计。模型算错了没人能发现。 |
| 4 | 19 个工具为什么只暴露 7 个？ | 选工具本质是分类，候选从 19 降到 5，准确率提升【Z】倍。 |
| 5 | 口径漂移怎么根治的？ | 口径进知识库 + 视图固化 + 模型禁止自行计算，三处同时收口。 |
| 6 | 样本不足为什么单独设计字段？ | 判断逻辑会被各入口各写一遍；字段只有一个来源。 |
| 7 | 你怎么保证不重复下单？ | 幂等键 + 服务端唯一索引 + 超时只查单不重发。 |
| 8 | AI 能不能自己审批？ | 不能，审批入口不存在——不是拦住，是够不着。 |
| 9 | 越权怎么拦？ | 前置拦截器在服务端工具入口，模型绕不过。提示词不是约束。 |
| 10 | 重试预算和重试次数差在哪？ | 预算是额度概念（LLM 与工具分开计），到顶强制收口，防循环。 |
| 11 | State 里为什么存 budget？ | 防死循环和成本失控，是失败降级的依据。 |
| 12 | 澄清为什么要"一次只问一个"？ | 变成问卷就没人用了；缺失槽位按业务优先级排序，只问当前阻塞的那个。 |
| 13 | RAG 引用失效合同怎么办？ | 元数据带有效期，检索强制过滤，出答案前校验条款存在且有效。 |
| 14 | 知识库为什么不存库存数字？ | 实时数字必须走工具；知识库只回答"规定是什么"。混用是翻车主因。 |
| 15 | 你说工具调用可观测，具体看什么？ | 失败率、P95 耗时、平均调用次数、易混工具对，按工作流聚合。 |
| 16 | 数据库约束和代码校验重复吗？ | 故意重复。库约束挡"新入口绕过"，代码校验给"友好提示"。 |
| 17 | 那个准确率怎么算的？ | 先说口径六要素，再说数字，主动说明是模拟环境 200 条。 |
| 18 | 评测集会过拟合吗？ | 会。所以按工作流分层抽样，长尾场景留出做验证集。 |

## 八、讲稿版本

### 8.1 三分钟版（约 650 字）

> 这个项目是在一个供应链 SaaS 的**采购管理模块**里植入 AI 助手，服务的是企业的采购员和采购主管。
>
> 在这之前，系统只记录不协助。采购员建单要跨四个页面：查库存算数量、翻历史比价、看供应商准时率、再去填单；物流延迟了系统只弹红点，要人自己判断"这单影响哪些客户订单、库存还能撑几天、换供应商来得及吗"，一次要二十分钟。
>
> 所以我们做了一个采购域的 Agent，把采购员每天做的四件事做成七条编排流程：建单、比价、审批前审阅、进度巡检、到货异常处置、供应商风险、制度问答。
>
> 架构上分三段。**模型只做理解和表达**——判意图、抽槽位、把结果说成人话；**所有数字由代码算**——补货量、供应商评分、影响面、异常检测都是确定性函数；**治理层兜底**——审批入口根本不存在，写操作有幂等键和审计。
>
> 我主要负责路由、工作流编排、工具契约、四个计算模块，以及幂等和审计的落库方案。
>
> 技术上最关键的三个决定：一是**工作流先行**，19 个工具按工作流裁剪成每轮 4~7 个，因为选工具本质是分类，候选越多越容易错；二是**指标口径进知识库、计算下沉到视图**，否则同一个准时率在三个入口会给出三个数；三是**危险动作不注册成工具**，让模型"够不着"而不是"被拦住"。
>
> 做完最大的坑是重复建单——提示词约束在并发下必然击穿，最后靠幂等键和服务端前置拦截解决。也正因为这个，我才理解"提示词是建议不是约束"。
>
> 结果是在 200 条工具选择评测集和 30 家供应商口径用例上，工具选择准确率从【A%】到【B%】，三个入口口径一致性 100%，越权拦截 100%、零重复单。

### 8.3 讲的时候三条纪律

1. **前 1 分钟不出现任何框架名**——先讲采购员每天在干什么；
2. **数字必带口径**——说"准确率 82%"后面必须跟"200 条评测集、模拟环境、优化前 61%"；
3. **主动暴露边界**——跨工作流复合请求要两轮、加权系数是拍的没有数据支撑。**主动说边界比被问出来强十倍。**
